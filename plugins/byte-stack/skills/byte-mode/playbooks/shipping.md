### Shipping

**The owner lands PRs. Merge only on the user's word, squash only, then clean up the branch.**

1. **Confirm the ask.** Merge a PR only when the user says to. A Decision subagent never stands in for that, even under `--auto`. A green babysit is not that word.
2. **Know who merges.** The repo owner merged all 30 of the most recent merged PRs by hand, release PRs included, and none had auto-merge set. The repo setting allows auto-merge, but nothing in the repo's files arms it or calls `gh pr merge`, and no workflow listens for a merge queue. Branch protection for `main` could not be read, the repo has no CODEOWNERS file, and the 105 PRs have no reviews. Without the user's word, report the PR merge-ready and hand it to the owner.
3. **Check before it lands.** Every check passes on the current head (`gh pr checks <pr>`). The title is right, because it becomes the commit on `main` and decides the next version. For a PR that changes code a doc describes, offer `/byte-docs-review pr` to the user. It is user-invoked and runs locally only, so its findings never block a merge.
4. **Merge with a squash merge.** `docs/directives/git-and-prs.md` says PRs to `main` are squash-merged only. That is a convention, not a setting: the repo also allows merge commits and rebase merges. The last 30 merged PRs each landed as one single-parent commit, and the only two merge commits in history predate the directive. No PR is stacked, so there is no merge order or retarget to manage.
5. **Confirm it landed.** Read the PR back with `gh pr view <pr>` and check that it reads merged.
6. **Clean up.** `git switch main`, `git pull`, then `git branch -D <branch>`. `-D` is needed because a squash merge leaves the branch's commits off `main`. GitHub deletes the remote branch on merge (a repo setting), so this step is local only. A SHA for `.git-blame-ignore-revs` exists only after the merge, so it goes in a follow-up PR.
7. **Expect the release PR.** The push to `main` runs `.github/workflows/release.yml`. After a `feat` or `fix` merge, release-please opens the release PR or updates the open one. A `refactor`, `docs`, `chore`, `test` or `ci` merge makes no release of its own. CI on that push runs scope `tested` when a green PR run already tested the tree.
8. **Stop at the merge.** Nothing deploys on merge: the repo's workflows are CI, PR checks, Release and New module proof, and none touches the VPS. Production runs a tagged release, and upgrading it is the operator's `docs/how-to/upgrade-production.md`. An agent never runs a step there marked `**Stop:**` without the operator's go-ahead for that step (`docs/directives/production-safety.md`).

**Release PRs.** release-please makes every version after `1.0.0`, never a person. The release PR is titled `chore(main): release <version>` and holds only `package.json`'s version, `.release-please-manifest.json` and CHANGELOG.md. Do not add commits to it. Merging it tags the merge `v<version>` and makes the GitHub release. Its merge runs CI scope `text`. Production runs releases, so the open release PR is merged, and its Release run tags it, before an upgrade (`docs/how-to/upgrade-production.md`). The owner merged #215 and #229. Opening it needs the repo setting "Allow GitHub Actions to create and approve pull requests", or the Release run fails. Two discrepancies stand:

- Branch name. `docs/directives/versioning.md` and `scripts/names-check.ts` name the release branch `release-please--branches--main--components--bphs-connect`, the branch real release PRs (#215, #229, #234) use, and `names:check` exempts only that exact name. No release PR has run it in CI yet.
- CI. The release PR is opened with `GITHUB_TOKEN`, so its `CI` and `PR checks` runs wait at `action_required` and close as failed, with no jobs, once it merges. Merge it without them: it holds only release-please's files (`docs/directives/versioning.md`). A change to `package.json`'s `version` alone makes no doc stale, so `docs:stale` passes it (`docs/directives/git-and-prs.md`).

**Reply:** what landed, who merged it and how you confirmed it, and whether a release PR opened or updated.
