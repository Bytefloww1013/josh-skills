### Autopilot-full

**You own the verdicts, not the merge. Each PR runs to green and reviewed on its own, then merges only when the user says to.**

Not established in bphs-connect: an agent merging a PR on its own. `docs/directives/git-and-prs.md` says to merge a PR only when the user says to. `byte-gh-issue-claim` says a Decision subagent never stands in for that, even under `--auto`. The 30 most recent merged PRs all show the repo owner's account as `mergedBy`. No file in the repo arms auto-merge or calls `gh pr merge`, though the repo's "Allow auto-merge" setting is on. Here, full autonomy runs up to the merge, and the merge waits on the user's word.

1. **Fix the queue and the user's gates.** The queue is a list of GitHub issues; `ready-for-agent` marks one fully specified for an agent and `ready-for-human` one that needs a person (`docs/agents/triage-labels.md`). `docs/directives/plans.md` says pushing and opening a PR never happen without the user's say-so, and that a feature's plan is questioned with the user over several rounds and built only on their go-ahead. `docs/skills/byte-gh-issue-claim.md` says `--auto` runs to an open PR without asking, and the repo does not say which wins. It also does not say whether one merge instruction covers a whole queue. Confirm both with the user.
2. **Run each issue through `byte-gh-issue-claim`.** The user invokes `/byte-gh-issue-claim <N> --auto`. It runs to an open PR without asking, because `--auto` is the say-so for that PR. Each gate goes to a Decision subagent, which never picks a `one-way-door` option. Where the skill's defaults differ, the repo's directives win (`docs/skills/byte-gh-issue-claim.md`): the plan file, the notes block in `AGENTS.md`, and the visual check on `docs/verify/scratch-server.sh start`, never the real `DATA_DIR`. Each run needs a clean tree (`git status --porcelain` empty) and branches from `origin/<base>`, so runs in one checkout go one after another. For two at once, the user starts each in its own worktree, and each scratch server gets its own `PORT` and `ROOT` (**principle-separate-before-serializing-shared-state**).
3. **Never stack.** Branch every PR from `main` and target `main`, as all 105 PRs in the repo do. PR checks and CI run for PRs to `main`; a pushed branch alone gets neither, though `gh workflow run CI --ref <branch>` starts CI by hand.
4. **Prove each PR before you call it ready.**
   - Run `docs/verify/quick-check.sh` after each phase.
   - Run the branch's `docs/verify/verify-done.sh`, copied from `docs/verify/verify-done.template.sh` (git ignores it) with the issue's own checks added. Exit 0 means done.
   - Under `--auto`, wait for the last CI run with `gh run watch <id> --exit-status`. Then `gh pr checks <pr>` must pass: `Stale docs, branch and title`, `Fast checks`, `Typecheck, test, build` and `Super-Linter`.
   - Review with `code-review` against `main` (Standards and Spec, in parallel sub-agents). Run `review-team` only when the user asks for it (`docs/skills/review-team.md`). Call the `migration-reviewer` agent when the branch adds a file under `server/db/migrations/` or changes a `schema.ts`, and the `module-boundary-reviewer` agent when it changes files in two or more of `foundation/<id>/`, `modules/<id>/` and the kernel (`.claude/agents/`). No PR in the repo has a GitHub review, so these are the review.
   - Every doc the change makes stale is edited in the PR, or excused with a `docs-unaffected: <doc> - <reason>` line in the body, drafted in `tmp/pr-body.md` (git ignores it), which `quick-check.sh` and `verify-done.sh` read.
5. **Rebase only when `main` moved.** Run `git fetch origin`. If the base moved, run `git rebase origin/<base>` and re-run the tests. Run `guard-branch` before every commit and push. Push each phase with `git push -u origin <branch>`, and after the final squash or a rebase with `git push --force-with-lease -u origin <branch>`. Never force without the lease, and never push any branch but the issue's.
6. **Merge on the user's word.** PRs to `main` are squash-merged only. The PR title becomes the commit on `main` and sets the next version: `feat` is MINOR, `fix` is PATCH (MINOR when it adds a migration), `!` is MAJOR, and `refactor`, `docs`, `chore`, `test` and `ci` make no release. After the merge, run `git switch main`, `git pull`, then `git branch -D <branch>`. A merged `feat` or `fix` makes the Release workflow open or update the release PR, `chore(main): release <version>`. That PR also merges only when the user says to.
7. **Stop and ask where the repo says to.** Stop when `gh auth status` fails, when every option at a gate is a `one-way-door` (the Decision subagent replies `STOP`), when a slice would break a Guardrail, or when a step has a `**Stop:**` line (`docs/directives/production-safety.md`).

PR body: draft it in `tmp/pr-body.md` with the sections of `.github/pull_request_template.md` (`docs/skills/pr.md`), and name the branch's issue in it, because `docs:stale` fails a draft that does not (`docs/directives/git-and-prs.md`). The `byte-gh-issue-claim` body also lists each Auto decision in one line under `--auto`. The `pr` skill's `## Merge Danger` section, whose `Door` line says one-way or two-way, is not in the template. See `playbooks/opening-a-pr.md`.

**Reply:** each PR with its link, its checks at the head, its review findings and its issue's door label, what merged on the user's word, the Auto decisions, and the gates still open. Lay out the gates as the **ketchup** helper's action items.
