### Multi-phase or multi-PR plan

**You own the plan, not the code. Write it, hand it back, and build nothing until the user gives the go-ahead.**

1. Pick the shape by size.
   - One issue, several phases, one PR: a feature plan per `docs/directives/plans.md`. Steps 2 to 6 cover it.
   - More than one PR: a spec and its tickets. The `chief-of-staff` skill routes large chunks of work through the `to-spec` skill, then `to-tickets`, then `implement-spec`. All three are user-invoked. `to-spec` publishes the spec as a GitHub issue labelled `ready-for-agent`. `to-tickets` publishes one issue per tracer-bullet ticket, blockers first, as sub-issues when the source is an issue, with GitHub's native blocking edges and the `ready-for-agent` label. It never closes or modifies the parent. Precedent: spec #236 has sub-issues #237 to #240, and #237, the tracer bullet, blocks the other three. `implement-spec` builds the whole spec on a single integration branch, but #237 went in as its own PR (#241, "Closes #237 (part of #236)"), so the repo's precedent is one PR per ticket.
   - Too big for one session and still unclear: the user-invoked `wayfinder` skill charts a map issue labelled `wayfinder:map`, with decision tickets as its child issues. By default it plans and does not build. A session resolves at most one ticket, research tickets aside.
   - `docs/agents/issue-tracker.md` holds the `gh` commands for sub-issues, labels and blocking edges.
2. Question the user over several rounds before writing. Open the first round with your reading of the user's goal and the problem behind it, by the **in-your-own-words** helper, so a wrong reading surfaces before the plan does. Then run the **sharpen** helper on the ask, and put its rewrite to the user as a proposed scope, with every choice in it left open.
3. Write `<feature_name>-plan.md` at the repo root. Build it from phases, each made of actionable slices, each slice a `- [ ]` checkbox at the start of its line. `.gitignore` ignores every root `*-plan.md`, so the plan is a working file that never reaches `main`, and the PR body and the code's commits are the record of the work (`docs/directives/plans.md`). No plan stays in the repo to copy, so use this shape: a title naming the issue, as in `# Form builder tracer plan (issue #223)`, the branch, the rules for working the plan, `## Decisions`, then `## Phase <n> - <name>` sections. The rules: run `bun run typecheck` and the touched test files after each slice, `docs/verify/quick-check.sh` after each phase, and commit the phase's code once its boxes are ticked. A plan may add gate rules of its own to its rules block, such as "Never push, and never open the PR, without the user's say-so."
   - Order the phases so each builds on a settled base. Removal of code the plan makes dead comes first, then scaffold (a prefactor, the schema and its migration, the shared types), then the routes and pages that use them (**principle-subtract-before-you-add**, **principle-foundational-thinking**).
   - For a rewrite or migration, aim each phase at the target shape and write no compatibility code to keep the old path alive. Name in the rules block any slice that may leave the typecheck or tests red, the one exception Sequence Work into Verifiable Units in `SKILL.md` allows. Each phase still ends with `docs/verify/quick-check.sh` exiting 0 before its commit (**principle-outcome-oriented-execution**).
4. Name each PR's branch `<descriptor>/<action>-issue<N>-<description>`. `docs/directives/git-and-prs.md` holds the descriptor and action lists. Every PR targets `main` and is squash-merged. No PR in the repo is stacked on another PR's branch. A phase is a commit on the issue's branch, not a PR (plans.md commits once per phase), and commit subjects follow Conventional Commits. The squash merge leaves one commit on `main`, titled by the PR title, whose type comes from the branch's descriptor. A ticket is unblocked when every blocker is closed.
5. Plan the Definition of Done. The branch's `docs/verify/verify-done.sh` is copied from `docs/verify/verify-done.template.sh`, gets one check per Definition of Done item, and is ignored by git. Its plan check fails while any line starts with `- [ ]`. It finds this plan with no edit when the plan's title names the issue as `#<N>` (`docs/directives/plans.md`).
6. Write the plan only. Hand back the path and stop. Implement nothing until the user gives the go-ahead. Nothing is pushed or opened as a PR here; for that, see "Push and PR" below.

**Push and PR.** `docs/directives/plans.md` defers to `docs/directives/git-and-prs.md`. A branch may be pushed without asking. A PR opens only with the user's say-so, given case by case, and `/byte-gh-issue-claim <N> --auto` is that say-so for the issue's own PR. A plan may add a stricter rule of its own in its rules block, and that rule holds for that plan.

**Two plan files.** The user-invoked `/byte-gh-issue-claim` writes its own `temp-gh-issue<N>-implementation.md` from its template and keeps it out of git through `.git/info/exclude`. That plan has `## Decisions` (Task, Guardrails, Definition of Done), an `## Ownership` table, and a last phase named "Verify + cleanup". `docs/skills/byte-gh-issue-claim.md` says the repo's directives come first where the skill's defaults differ: here a feature plan is `<feature_name>-plan.md` at the repo root, which `.gitignore` keeps out of git. The skill's `check-plan.sh` counts unticked slices and prints the next one on a `NEXT:` line. It warns when git tracks the plan, and it fails on any of the five headings or fields it requires that the plan lacks.

Not established in bphs-connect: a plan checker written for `<feature_name>-plan.md`, a CI job that reads plan files, or a plan item in the PR template.

**Reply:** the plan path, the phases or tickets with their blocking edges, the decisions taken, and the questions still open.
