### Feature

**You own the design. Plan first, build only after the go-ahead, and finish on the repo's own gates.**

1. Branch from the issue. Name the branch `feature/<action>-issue<N>-<description>` before its first commit (`docs/directives/git-and-prs.md` holds the descriptor and action lists). Commit subjects follow Conventional Commits, e.g. `feat(forms): ...`.
2. Learn the area. Read `docs/references/architecture.md` (the map), `docs/references/modules.md` and the module's `README.md`. CLAUDE.md says to query CodeGraph before Read, Grep or Glob when the target is code. Check `docs/adr/` for decisions already taken. Domain words come from `docs/references/project-glossary.md`. Do not create a `GLOSSARY.md`, even when a skill (`domain-modeling`, `improve-codebase-architecture`) names one. When the feature reaches a subsystem you have not traced, or crosses modules, run the **how** helper on it. The architect run in step 4 reuses it as its Phase A.
3. Plan per `docs/directives/plans.md`. Question the user over several rounds, opened as `playbooks/multi-phase-plan.md` step 2 says. Write the plan from phases of slices, each slice with a checkbox. Implement nothing until the user gives the go-ahead. A question a round cannot settle by talk can be settled by a prototype first (`playbooks/prototype.md`).
   - While questioning, test each control and option against the work `PRODUCT.md`'s Product Principles put first (fast, keyboard-operable entry and trustworthy answers), and propose cutting what does not serve it. The user decides the scope (**principle-experience-first**).
   - When the feature changes an existing module, plan it as if the requirement had been there from the start, as the Form builder did: built Forms are stored beside the code Forms, so the one lookup of registered Forms returns both (`docs/adr/0004-forms-built-in-the-app.md`, **principle-redesign-from-first-principles**). Order the phases as `playbooks/multi-phase-plan.md` step 3 says.
4. Name the data shape before writing logic, in the module system's terms. Choose its organizing structure per **principle-model-the-domain**, and fit the tables and types to the routes, hooks and pages that read them (**principle-foundational-thinking**):
   - A feature's tables, rules, API, pages, seed, tests and README go in its module folder.
   - A new module goes through the repo's `add-module` skill (`bun run new-module <id> [--foundation]`, ending with `docs/verify/quick-check.sh`).
   - A new table, column or index goes in the module's `server/schema.ts`, and the New migration playbook (`playbooks/new-migration.md`) makes its migration.
   - If two accounts can save the same row, decide what the second save does before writing the route. Edits in this app refuse a save over a newer one with 409 `stale_version` (`docs/references/api-errors.md`), as the Form builder's working copy does (`modules/forms/README.md`).
   - A status the clock or other rows decide is worked out, never stored, as `taskStatus` in `modules/tasks/shared/tasks.ts` is.
   - Data from another module comes through a server hook or a web slot, or through its public API (`server/index.ts`, `shared/index.ts`, `web/index.ts`) with the module named in the manifest's `dependsOn`. If the feature changes the shape of a hook, slot or public API, move its callers and drop the old shape in this PR (**principle-migrate-callers-then-delete-legacy-apis**).
   - Precedent: #241 gave each Form question type one entry in a shared question type table, `modules/forms/shared/question-types.ts`. Its type, `{ [K in QuestionType]: Entry<K> }`, makes the compiler name a type still missing its entry (**principle-type-system-discipline**).
   - When the shape has no precedent in the architecture map, the module docs, an ADR or a sibling module, design it at least twice with the **architect** helper (**principle-exhaust-the-design-space**). Its Phase B runs **arena** with at least two structurally distinct sketches. Give each runner the project glossary and the module rules above as grounding. Run it during the question rounds: the go-ahead is its checkpoint (Helpers in `SKILL.md`). A pick that changes the approved plan goes back to the user.
5. Build phase by phase. Hold to the AGENTS.md gotchas that apply:
   - After changing `app.modules.ts`, a manifest or a `module.ts`, run `bun run modules:gen` and commit the generated registries with the change.
   - Every API route's first handler is its access declaration. Accept new routes with `bunx vitest run server/access/route.test.ts -u` and read the `server/access/route-declarations.txt` diff.
   - A route parses its body once with the module's shared Zod schema (`json(schema)` from `server/http.ts`), and the service trusts that type (**principle-boundary-discipline**). A rule the page and the server both judge is a pure function in `shared/`, as `shared/access-change.ts` is.
   - A `startup`, a job or a webhook runs again after a restart or a retry. Read what is there and apply only the difference, as `sendDueSeries` (`modules/tasks/server/series.ts`) and `ensureDefaultLists` (`modules/assets/server/lists.ts`) do (**principle-make-operations-idempotent**).
   - Anything that touches production or a backup follows `docs/directives/production-safety.md`. Never develop or test against a real backup or a copy of the live database.
   - A race between two saves, a retry or a restart, where tests reach the bad order only by luck, is a candidate for formal verification. Offer the **create-formal-verification-skill** helper in the reply, for after the merge.
6. Verify each phase:
   - After each slice, run `bun run typecheck` and its touched tests, and tick the slice only when they pass. Never start the next slice or phase on red, except as Sequence Work into Verifiable Units in `SKILL.md` allows (**principle-sequence-verifiable-units**).
   - Fast loop: `bunx vitest run <path>`. Use `bun run test`, never `bun test`.
   - After each phase: bring its docs up to date as `docs/directives/plans.md` says (generated docs change through their source and `bun run docs:gen`). Then `docs/verify/quick-check.sh` (it formats the tree in place first), and commit the phase with its slices ticked.
   - UI: `docs/verify/scratch-server.sh start` (seeded, port 3388), then `node docs/verify/browser.mjs <address>...`. It fails on a console error, page error or error page. Follow `playbooks/visual-parity.md` for how screenshots are judged. Check each disabled control's reason and the keyboard path, as the Do's in `DESIGN.md` ask, and the empty list and the error state (**principle-experience-first**).
   - A new route goes into the `ROUTES` list in `docs/verify/routes-smoke.mjs`. Run it with `SKIP_BUILD=1 node docs/verify/routes-smoke.mjs`.
7. Prove done. Copy `docs/verify/verify-done.template.sh` to `docs/verify/verify-done.sh` (git ignores it). Add one check per Definition of Done item under "This issue's checks". Each check runs the behavior itself, such as a `named_test`, a `browser.mjs` run or a script against the scratch server, never a grep of the diff or a file's existence (**principle-prove-it-works**). Exit 0 means done. It fails while any plan slice is unticked or local `main` is ahead of `origin/main`.
8. Run **Opening a PR** (`playbooks/opening-a-pr.md`).

Plan file: the plan is `<feature_name>-plan.md` at the repo root, its title naming the issue as `#<N>`. `.gitignore` keeps it out of git, and the code is committed per phase (`docs/directives/plans.md`). It lives only in the checkout that wrote it, so put what a reviewer or the next session needs from it in the PR body or a handoff. `/byte-gh-issue-claim` (user-invoked) writes a git-excluded `temp-gh-issue<N>-implementation.md` instead, and `docs/skills/byte-gh-issue-claim.md` says the repo's directives win over that default. verify-done reads the temp file when it exists, else the plan whose title names the issue. If `/byte-gh-issue-claim` ran, its `byte-gh-issue-claim #<N>` notes block must also be gone from `AGENTS.md`, or verify-done fails.

Reviewers: the `review-team` skill runs specialist reviewer subagents when the user asks for a review. It also runs each reviewer agent in `.claude/agents/` whose description the change meets. When to call those agents yourself is the Review agents trigger in `SKILL.md`.

**Reply:** what you built, the data shape and why, the quick-check and verify-done output, open decisions.
