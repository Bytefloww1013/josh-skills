### Opening a PR

Invoked at the end of every other playbook. `docs/directives/git-and-prs.md` owns the rules below. Read it when one is unclear.

1. **Branch.** Name the branch `<descriptor>/<action>-issue<N>-<description>`, the description being two or three lower-case words joined by `-`, before its first commit, in place of any name the session hands over. Example: `feature/build-issue30-docs-context-system`. The descriptor and action lists live in the directive, and `bun run names:check` reads them. Branch from `main`: `git fetch origin && git switch -c <branch> origin/main`. Never push to `main`.
2. **Scope.** Every PR targets `main`. All 105 PRs so far do, and none is stacked on another PR's branch. CI picks its jobs by the paths a change touches, never by its size. A change to the docs system itself (the checks in `scripts/docs*`, the directives, the doc header) goes in a PR of its own, not with a feature.
3. **Commits.** Commit subjects follow Conventional Commits. `/byte-gh-issue-claim` commits each phase as `<type>(<scope>): <subject> (#<N>)`. Commit the generated module registries (`shared/modules.gen.ts`, `server/modules.gen.ts`, `web/src/modules.gen.ts`) and `bun.lock` with the change that made them. PRs are squash-merged, so the branch's commits never reach `main`. The PR title does.
4. **Docs.** Update every doc the change makes stale in the same PR. A doc whose `sources` the PR changes is edited too, or the PR body excuses it with a `docs-unaffected: <doc> - <reason>` line. Tests, seeds and a change to `package.json`'s `version` alone (a release PR) never make a doc stale.
5. **Body.** Draft it in `tmp/pr-body.md`. Git ignores the file, and `quick-check.sh` and verify-done read the same lines. Name the branch's issue in it as `#<N>`, outside HTML comments: `docs:stale` fails a draft that does not. Use the sections of `.github/pull_request_template.md`:
   - `## What and why`: what changes and why. Link the issue it closes (`Closes #<N>`).
   - `## How it was checked`: the tests, smokes or browser checks you ran and what they showed. Say what you did not check.
   - `## Docs unaffected`: one `docs-unaffected:` line per excused doc. Delete the section when there are none.
   - `## Merge Danger`: `**Door:**` one-way or two-way, and why. A two-way door is cheap to walk back (revert the commit, switch back to the `previous` image). A data-changing migration or a removed feature is one-way. `**Blast Radius:**` what a wrong change reaches, in a word or two (Forms, local-only), then what could break. For a one-way door, or a change to a public API, a hook, a slot, a migration or the kernel, take it from the **blast-radius** helper: what breaks beyond the diff, and the one fact the change is safe because of, with how far its proof got.
   - `## Checklist`: docs updated or none stale, `bun run format` run, and `format:check`, `lint` (no warnings), `typecheck` and `test` passing.
6. **Local gates.** Run `docs/verify/quick-check.sh` before you push. It runs `bun run format` in place, then every check `docs/verify/gate-checks.txt` marks `quick`. Expect one `PASS:` line per check, then `RESULT: PASS`. Then run the branch's `docs/verify/verify-done.sh`, copied from `docs/verify/verify-done.template.sh` (see `playbooks/feature.md`). Exit 0 means done. Checks tagged `ci` (the script tests, the route smoke, the new module proof) run only in CI. To try CI before opening the PR, run `gh workflow run CI --ref <branch>`.
7. **Title.** `<type>(<scope>): <subject>`, with the type the branch's descriptor maps to: `feature` to `feat`, `bug` to `fix`, `doc` to `docs`. `refactor`, `chore`, `test` and `ci` keep their names. The title becomes the commit on `main` and decides the next version (`docs/directives/versioning.md`). A `feat` is MINOR and a `fix` PATCH, a migration that only adds included. `refactor`, `docs`, `chore`, `test` and `ci` make no release. A PR is MAJOR when the upgrade needs the operator to act or cannot be undone by switching back to the `previous` image (a data-changing migration, a renamed or removed environment variable, a changed Zoho webhook contract, a removed feature). It takes `!` after its type and scope, such as `feat(assets)!:`, and its body says what the operator must do. Check branch and title with `bun run names:check --branch <branch> --title "<title>"`.
8. **Push and open.** Push the branch without asking. Open the PR only with the user's say-so, given case by case (`docs/directives/git-and-prs.md`). `/byte-gh-issue-claim` asks at its Step 9, and `--auto` is that say-so for the issue's own PR. Then `git push -u origin <branch>`, then `gh pr create --base main --head <branch> --title "<title>"` with the body from `tmp/pr-body.md`. `/byte-gh-issue-claim` squashes first: `git reset --soft $(git merge-base HEAD origin/main)`, one commit whose subject is the title, then `git push --force-with-lease -u origin <branch>`.
9. **Report.** Post the PR URL and the output of `gh pr checks <pr>`. Opening a PR does not merge it. Merge only when the user says to (`playbooks/shipping.md`). Drive the checks only when the user asks (`playbooks/babysit.md`).

**Two body templates.** The repo's `pr` skill ("Use when writing a PR body") has its own template: `## Summary`, `## Evidence` (Before and After), and `## Merge Danger`. `docs/skills/pr.md` says to fill the sections of `.github/pull_request_template.md` in this repo, and that the skill is written for any repo and does not know this repo's directives, glossary words or doc rules. The template has its own `## Merge Danger` (step 5). #245 follows it. The `pr` skill says to use words from `GLOSSARY.md`, which does not exist. The glossary is `docs/references/project-glossary.md`.

**Draft PRs.** The house directives (`docs/directives/git-and-prs.md`, `docs/directives/plans.md`) say nothing about them, none of the 105 PRs is a draft, and the `gh pr create` in `/byte-gh-issue-claim` passes no `--draft`. The vendored `implement-spec` skill does open a draft PR (steps 3 and 8 of `.claude/skills/implement-spec/SKILL.md`: open it after the first merge, mark it ready at the end), but `docs/skills/implement-spec.md` says it is written for any repo, not this one, and does not know this repo's directives.

Not established in bphs-connect: a worktree rule for opening a PR.
