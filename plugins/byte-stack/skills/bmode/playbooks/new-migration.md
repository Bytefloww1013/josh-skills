### New migration

**drizzle-kit writes the migration from the schema. A migration already on `main` stays as it is: a change to what it did is a new migration.**

Migrations run as the server starts, all pending ones in one transaction, and only go forward: production has no undo but the `previous` image or the pre-upgrade backup (`docs/how-to/upgrade-production.md`, Guidance).

1. **Change the schema where drizzle-kit reads it.** A new table, column or index goes in its module's `server/schema.ts` (`docs/references/modules.md`, Change a module). drizzle-kit reads only `server/db/schema.ts` and the `foundation/*` and `modules/*` `server/schema.ts` files (`drizzle.config.ts`). A table defined anywhere else is invisible to it, and moving one out of those files shows as a drop (AGENTS.md gotcha).
2. **Generate it.** Run `bun run db:generate --name <what>`, naming the table or change, as `0035_built_forms` does. It writes the SQL file, its snapshot and the journal entry in `server/db/migrations/`. Read the SQL it wrote before anything else. Commit the migration with the schema change that made it (`docs/how-to/upgrade-production.md`, Guidance).
3. **Edit only your own migration.** A migration not yet on `origin/main` may be edited. One on `origin/main` may not: `scripts/claude-edit-hooks.ts` refuses the edit, and `bun run migrations:check` fails when an entry that `origin/main` has changes its tag, its `when` or its SQL, because a database that applied it never runs the change (`docs/references/commands.md`). When `origin/main` gains a migration before yours merges, `migrations:check` fails until your entry's `idx` and `when` come after main's (`scripts/migrations-check.ts`).
4. **Rebuild a table the gotcha's way.** A migration runs inside one transaction with foreign keys on, where dropping a table other tables point at cascades or is refused, and `PRAGMA foreign_keys=OFF` does nothing. To rebuild one, set the tables that point at it and their `sqlite_sequence` rows aside and put them back, as 0023, 0024 and 0025 do (AGENTS.md gotcha). 0023's comments explain the pattern. drizzle-kit's own rebuild (`PRAGMA foreign_keys=OFF`, then `DROP TABLE`) holds only for a table nothing points at, as in 0044.
5. **Give each foreign key its `ON DELETE`.** drizzle-kit writes `ALTER TABLE ... ADD <col> ... REFERENCES` without the `ON DELETE` the schema asks for. `bun run migrations:fks` names each foreign key whose action differs from the snapshot's (`docs/references/modules.md`, Change a module).
6. **Weigh what it does to existing rows.** A migration that changes or removes data makes the PR MAJOR, because going back then needs the pre-upgrade backup. One that only adds keeps a `feat` MINOR and a `fix` PATCH (`docs/directives/versioning.md`). The title and the door follow `playbooks/opening-a-pr.md` steps 5 and 7.
   - A migration that moves or rewrites rows can be tested with `migratedBefore('<prefix>')` from the test kit (`server/testing/index.ts`), which migrates an in-memory database up to it and applies it with `next()`. Precedent: `modules/maintenance/server/migration.test.ts` for 0025.
   - A migration that rebuilds a table or merges data is rehearsed on a copy of a backup before it reaches production (`.claude/agents/migration-reviewer.md`). Staging runs any pushed branch on a production backup (`docs/how-to/run-staging.md`), so offer the operator the Upgrade staging playbook (`playbooks/upgrade-staging.md`) on `origin/<branch>`. Say in the PR body which rehearsal ran, or that none did.
7. **Run the checks.** Fetch `origin/main` first: `migrations:check` compares against it.
   - `bun run migrations:check`: the journal counts up with no gap, `when` only increases, and every entry on `origin/main` is unchanged.
   - `bun run migrations:fks`: each foreign key the SQL creates matches the snapshot.
   - `docs/verify/schema-drift.sh`: drizzle-kit would write no further migration, so the schema files and the last snapshot agree.
   - `bun run tables:refs`: a new reference to another module's table fails it. A change that adds or removes one runs `bun run tables:refs --write` and commits the new baseline (`docs/references/modules.md`, Boundaries).
   - `bun run test`: the test kit's `setup()` runs every migration on an in-memory database.
   All five are `quick` checks in `docs/verify/gate-checks.txt`, so `docs/verify/quick-check.sh` runs them too.
8. **Call the `migration-reviewer` agent.** Give it the base (`origin/main`), the diff and which migrations are new (`.claude/agents/migration-reviewer.md`). Fix each finding, then call a fresh one on the new diff.
9. Run **Opening a PR** (`playbooks/opening-a-pr.md`).

Not established in bphs-connect: how to renumber a migration after `main` gains one (generating it again with `db:generate` on the rebased branch is one way), a rule that a migration ships with a test of its own (the `migration.test.ts` files are precedent), a down migration (they only go forward), or a check that runs a branch's migrations on a copy of production data before the merge.

**Reply:** the migration's file name and what it does to existing rows, whether it changes or removes data and so the PR's door and version, each check and test with its result, the `migration-reviewer` answer, and which rehearsal ran or was offered.
