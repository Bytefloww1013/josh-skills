### Orchestrate

**You run the program, never the code. Subagents build, review skills check, and the user merges.**

For a standing project with many issues and PRs under one coordinator session. Not established in bphs-connect: a skill that runs such a program. This session is the coordinator, under bmode. The user-invoked skills it leans on (`to-spec`, `to-tickets`, `wayfinder`, `implement`, `retro`) are "written for any repo, not this one", so where they differ from the repo's directives, the directives win.

1. **Hold the user's gates.** Question the user over several rounds, then write the plan. Implement nothing until the user gives the go-ahead. The plan is `<feature_name>-plan.md` at the repo root. Git ignores it, and the code is committed after each phase (`docs/directives/plans.md`). A branch may be pushed without asking. Open each PR only with the user's say-so, given case by case (see Autonomy in `SKILL.md`). Never push to `main`, and merge a PR only when the user says to. PRs to `main` are squash-merged only (`docs/directives/git-and-prs.md`).
2. **Put the program in GitHub issues.** Issues and specs live on `Bytefloww1013/bphs-connect` and are worked with `gh` (`docs/agents/issue-tracker.md`). For a large chunk, the user runs `/to-spec`, then `/to-tickets` (`playbooks/multi-phase-plan.md` step 1). For one too big for a session and still unclear, `/wayfinder` charts a map of decision tickets first, and plans rather than builds. Tickets get the `ready-for-agent` label (`docs/agents/triage-labels.md`). A blocking edge uses GitHub's native dependencies: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`. A child issue is unblocked when every blocker is closed. Both lines come from the repo's wayfinding section of `docs/agents/issue-tracker.md`. Precedent: #236 has sub-issues #237 to #240, and #237, the tracer bullet, blocks the other three. A new issue follows the `byte-gh-issue` skill: a `[TYPE] <Action> <specific what and where>` title, its body sections, exactly one of `one-way-door` or `two-way-door`, and never a new label (`docs/agents/issue-tracker.md`).
3. **Review the issue set before the run.** Run `arch-skills:architecture-review-report` on the queue's issues, and settle its findings and Gaps with the user before step 4 starts (Helpers in `SKILL.md`, arch-skills).
4. **Do all work in subagents.** Start each with a fresh context (**principle-guard-the-context-window**). Talk through context pointers (research notes, commits), not pasted copies. Edits one script can make, run the script yourself instead of fanning them out. Put the subagents' shared recipe, checks and do-not-touch files in one file under `tmp/` that no subagent owns, and give each brief its absolute path, since `tmp/` is git-ignored and absent from worktrees (**principle-build-the-lever**). The plan is git-ignored too, so give its absolute path the same way.
   - One PR per ticket, each on its own branch from `main`, named `<descriptor>/<action>-issue<N>-<description>`, in its own worktree. A delegate (`byte-agent`, or under T3 a Neon implementor when `references/t3-model-routing.md` allows) builds it from its brief, or the user runs `/byte-gh-issue-claim <issue>` or `/implement <issue>` there. `implement` runs `tdd` at agreed seams and `code-review` at the end, and commits to the current branch, so start it on the ticket's branch. A claim run's plan file is the repo's `<feature_name>-plan.md`, not the skill's `temp-gh-issue<N>-implementation.md` (`docs/skills/byte-gh-issue-claim.md`). `names:check` enforces the branch name and title on every PR.
   - Each subagent owns named files and never pushes or switches branches. One in a shared checkout never commits either; one in its own worktree commits on its ticket's branch only. Each reports its changed files, commits and test output. Check `git diff --stat` against its ownership when it returns.
   - Split shared write targets before the fan-out. Each owner gets its own files and its own worktree, and each scratch server or routes smoke its own `PORT` and `ROOT`. An owner runs the generating command for a generated file its ticket needs (`bun run modules:gen`, `bun run db:generate`, `bun run tables:refs --write`, `server/access/route.test.ts` with `-u`, `bun install`), so its own checks pass. Nobody merges those files by hand. On a conflict in one after a rebase, take `main`'s copy and run the command again. Two tickets that each add a migration both take the next journal `idx`, which `bun run migrations:check` fails. No repo doc covers this. Per Separate Before Serializing Shared State, the second one deletes its migration and runs `bun run db:generate` again after the first is merged (**principle-separate-before-serializing-shared-state**).
   - A fan-out outside one-PR-per-ticket, such as a sweep of checks or a race between approaches, runs through the **swarm** helper. Its Frame step fixes the done predicate and each brief, and step 4 judges its `PASS`, `ISSUES` and `BLOCKED` reports by the SHAs they name.
5. **Judge the output, not the report.** Each phase ends with `docs/verify/quick-check.sh`. A branch proves done with its git-ignored `docs/verify/verify-done.sh`, written from `docs/verify/verify-done.template.sh`. Exit 0 means done. Read live state with `gh pr checks <pr>` and `gh run list --branch <branch> --limit 3`. The checks are `Stale docs, branch and title` (PR checks) and `Fast checks`, `Typecheck, test, build` and `Super-Linter` (CI).
6. **Review with the repo's skills.** Before you report a delegate's PR merge-ready, run `arch-skills:pr-erosion-check` on it with its issue as the yardstick, and send each Critical or High finding back to a fresh delegate (Helpers in `SKILL.md`, arch-skills). Under T3, the Sol review is the code review (`references/t3-model-routing.md`). Otherwise `code-review` runs Standards and Spec reviews in parallel sub-agents against a fixed point. `review-team` runs specialist reviewers once by default, and iterates only when the user asks. Call each review agent the Review agents trigger in `SKILL.md` names. No PR in the repo has a GitHub review, and no review bot is configured.
7. **Keep memory outside the session.** Not established in bphs-connect: a wiki or other store for a program's memory. Keep it in the issues, the PR bodies and the handoffs, and agree any other place with the user before the first write. Date every claim, and cite the commit for a claim about code. The handoff-guard hook watches every main session, on any model. 35k tokens before the autocompact it requires the `byte-handoff` skill, and only handoff work is allowed until it runs. It ignores subagent events. Handoffs go in the git-ignored `handoff/` and are never committed.
8. **Learn from the runs.** `retro` is user-invoked: after a subagent session where something went wrong, offer `/retro`. Not established in bphs-connect: how often to run one. A mechanical finding becomes a lint rule or a check listed in `docs/verify/gate-checks.txt`. A judgment call becomes a `[judgment]` rule proposed to the user, or an AGENTS.md gotcha (**principle-encode-lessons-in-structure**).
9. **Keep every agent off production.** A how-to step with a `**Stop:**` line runs only on the operator's go-ahead, given in that session for that step. Never develop or test against a real backup or a copy of the live database. Use the seed (`docs/directives/production-safety.md`).

Cloud sessions: `gh issue` and `gh pr` use GraphQL, which a cloud session blocks. Use the `gh api` forms in `docs/agents/issue-tracker.md`. A cloud session installs no plugins, so steps 3 and 6 fall back as Helpers in `SKILL.md` says.

Not established in bphs-connect: stacked PRs (every PR in the repo targets `main`), an agent merging a PR (the repo owner's account merged every merged PR, so an agent merge is not distinguishable, and the repo has no auto-merge tooling), and a verifier per PR on a different model.

**Reply:** what landed against the goal, each issue and PR with its link, live checks and erosion-check verdict, what was dropped and why, and the merges and decisions waiting on the user, laid out as the **ketchup** helper's action items.
