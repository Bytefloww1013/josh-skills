### Orchestrate

**You run the program, never the code. Subagents build, review skills check, and the user merges.**

For a standing project with many issues and PRs under one coordinator session. The skill for this is `chief-of-staff`, installed from `mattpocock/skills` and still in progress upstream. It is user-invoked (`/chief-of-staff`, `disable-model-invocation: true`). It and the skills it runs (`to-spec`, `to-tickets`, `implement-spec`, `retro`, `tdd`) are "written for any repo, not this one", so where they differ from the repo's directives, the directives win (`docs/skills/chief-of-staff.md`).

1. **Hold the user's gates.** Question the user over several rounds, then write the plan. Implement nothing until the user gives the go-ahead. The plan is `<feature_name>-plan.md` at the repo root. Git ignores it, and the code is committed after each phase (`docs/directives/plans.md`). A branch may be pushed without asking. Open each PR only with the user's say-so, given case by case (see Autonomy in `SKILL.md`). Never push to `main`, and merge a PR only when the user says to. PRs to `main` are squash-merged only (`docs/directives/git-and-prs.md`).
2. **Put the program in GitHub issues.** Issues and specs live on `Bytefloww1013/bphs-connect` and are worked with `gh` (`docs/agents/issue-tracker.md`). For a large chunk, `chief-of-staff` runs `to-spec`, then `to-tickets`, then `implement-spec`. Tickets get the `ready-for-agent` label (`docs/agents/triage-labels.md`). A blocking edge uses GitHub's native dependencies: `gh api --method POST repos/<owner>/<repo>/issues/<child>/dependencies/blocked_by -F issue_id=<blocker-db-id>`. A child issue is unblocked when every blocker is closed. Both lines come from the repo's wayfinding section of `docs/agents/issue-tracker.md`. Precedent: #236 has sub-issues #237 to #240, and #237, the tracer bullet, blocks the other three. A new issue follows the `byte-gh-issue` skill: a `[TYPE] <Action> <specific what and where>` title, its body sections, exactly one of `one-way-door` or `two-way-door`, and never a new label (`docs/agents/issue-tracker.md`).
3. **Do all work in subagents.** Start each with a fresh context (**principle-guard-the-context-window**). Talk through context pointers (research notes, commits), not pasted copies. Edits one script can make, run the script yourself instead of fanning them out. Put the subagents' shared recipe, checks and do-not-touch files in one file under `tmp/` that no subagent owns, and give each brief its absolute path, since `tmp/` is git-ignored and absent from worktrees (**principle-build-the-lever**). The plan is git-ignored too, so give its absolute path the same way. The repo has two routes:
   - `implement-spec`: one integration branch for the whole spec. A fresh implementer subagent takes each ticket, in its own worktree on its own branch, and builds it with `tdd`. A merger subagent merges each finished ticket into the integration branch. A changed frontier starts new implementers. When all tickets are done, run `code-review` on the integration branch and fix its findings in one fresh implementer. Then clean up the implementer worktrees.
   - One PR per issue, the user-invoked `/byte-gh-issue-claim <issue>` flow. Its plan file is the repo's `<feature_name>-plan.md`, not the skill's `temp-gh-issue<N>-implementation.md` (`docs/skills/byte-gh-issue-claim.md`). Each subagent owns named files, never commits, pushes or switches branches, and reports its changed files and test output. Check `git diff --stat` against its ownership when it returns.
   Every PR targets `main` from a branch named `<descriptor>/<action>-issue<N>-<description>`. `names:check` enforces the branch name and title on every PR.
   Split shared write targets before the fan-out. Each owner gets its own files and its own worktree, and each scratch server or routes smoke its own `PORT` and `ROOT`. An owner runs the generating command for a generated file its ticket needs (`bun run modules:gen`, `bun run db:generate`, `bun run tables:refs --write`, `server/access/route.test.ts` with `-u`, `bun install`), so its own checks pass. Nobody merges those files by hand. On a conflict in one, the merger takes the integration branch's copy and runs the command again. Two tickets that each add a migration both take the next journal `idx`, which `bun run migrations:check` fails. No repo doc covers this. Per Separate Before Serializing Shared State, the second one deletes its migration and runs `bun run db:generate` again after the first is merged (**principle-separate-before-serializing-shared-state**).
   A fan-out outside those two routes, such as a sweep of checks or a race between approaches, runs through the **swarm** helper. Its Frame step fixes the done predicate and each brief, and step 4 judges its `PASS`, `ISSUES` and `BLOCKED` reports by the SHAs they name.
4. **Judge the output, not the report.** Each phase ends with `docs/verify/quick-check.sh`. A branch proves done with its git-ignored `docs/verify/verify-done.sh`, written from `docs/verify/verify-done.template.sh`. Exit 0 means done. Read live state with `gh pr checks <pr>` and `gh run list --branch <branch> --limit 3`. The checks are `Stale docs, branch and title` (PR checks) and `Fast checks`, `Typecheck, test, build` and `Super-Linter` (CI).
5. **Review with the repo's skills.** `code-review` runs Standards and Spec reviews in parallel sub-agents against a fixed point. `review-team` runs specialist reviewers once by default, and iterates only when the user asks. No PR in the repo has a GitHub review, and no review bot is configured.
6. **Keep memory outside the session.** The generic `chief-of-staff` skill keeps a wiki of linked pages. Use a shared one if it exists. Otherwise agree its location with the user before the first write. Date every claim, and cite the commit for a claim about code. No wiki is established in bphs-connect. The handoff-guard hook watches every main session, on any model. 35k tokens before the autocompact it requires the `byte-handoff` skill, and only handoff work is allowed until it runs. It ignores subagent events. Handoffs go in the git-ignored `handoff/` and are never committed.
7. **Learn from the runs.** Run a retro on about one in five subagent sessions, including those `implement-spec` dispatches. Pick the ones where something went wrong first. A mechanical finding becomes a lint rule or a check listed in `docs/verify/gate-checks.txt`. A judgment call becomes a `[judgment]` rule proposed to the user, or an AGENTS.md gotcha (**principle-encode-lessons-in-structure**).
8. **Keep every agent off production.** A how-to step with a `**Stop:**` line runs only on the operator's go-ahead, given in that session for that step. Never develop or test against a real backup or a copy of the live database. Use the seed (`docs/directives/production-safety.md`).

Cloud sessions: `gh issue` and `gh pr` use GraphQL, which a cloud session blocks. Use the `gh api` forms in `docs/agents/issue-tracker.md`.

Not established in bphs-connect: stacked PRs (all 105 PRs target `main`), an agent merging a PR (all 102 merged PRs show the repo owner's account as the merger, so an agent merge is not distinguishable, and the repo has no auto-merge tooling), and a verifier per PR on a different model.

**Reply:** what landed against the goal, each issue and PR with its link and live checks, what was dropped and why, and the merges and decisions waiting on the user, laid out as the **ketchup** helper's action items.
