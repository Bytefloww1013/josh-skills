### Upgrade production

**Ship only a tagged release that rehearsed green, and run each `**Stop:**` step only on the operator's go-ahead for that step, given in this session.**

`docs/how-to/upgrade-production.md` is the procedure. Follow its steps in order and quote each one's "Expect" result. The old version keeps serving until the switch, its step 8. The rehearsal, its step 7, comes before it: the switch never runs without a green result block for the same commit and backup. Throughout, never run `docker compose down -v`, remove `bphs-connect-data` or prune volumes: each can delete the data (`docs/how-to/upgrade-production.md`, Guidance).

1. **Release first.** Production gets only a tagged release of `main` (`docs/directives/versioning.md`). Check that no release PR is open (`gh pr list --state open --head release-please--branches--main--components--bphs-connect` lists none) and that the newest release exists (`gh release view` names its tag). An open release PR is merged only on the user's word (`playbooks/shipping.md`), and its Release run then tags it. Until both hold, stop and report what is waiting.
2. **Read what the version asks.** A new MAJOR release means going back may need the backup, and the PR behind it says what the operator must do (`docs/how-to/upgrade-production.md`, Guidance). Read the CHANGELOG.md sections since the version production runs, each PR listed under "BREAKING CHANGES", and this release's one-off notes in `TODO.md`, under Production. Report what they ask of the operator before you go on.
3. **Note the rollback point.** Run the how-to's step 1 and keep the release tag and commit it prints: a rollback goes by the commit. Run its step 2, `docs/how-to/back-up-database.md` (Take one now), and keep the backup's file name. If the backup fails, stop.
4. **Get the version and build it.** Run the how-to's steps 3 to 6: pull with `--tags`, then check that `git describe --tags --always` prints the newest release's tag with no suffix. With a suffix and a release PR open, it merges only on the user's word (`playbooks/shipping.md`); after its Release run makes the tag, pull again. With none open, run `git switch --detach v<version>`, as its step 4 says. Step 3's rollback point stays as it was. Then tag the running image `previous` and build. On a failure, stop: nothing has changed yet.
5. **Rehearse.** The how-to's step 7 is the Upgrade staging playbook (`playbooks/upgrade-staging.md`), given the commit `git rev-parse --short HEAD` prints on the VPS and the backup from step 3 here. A rehearsal on another commit or another backup does not count. Go on only when its result block reads green, names this commit and this backup, and shows `1 applied now` or more if this version adds a migration. On red, stop: the old version is still serving on its own database. Keep the output and the backup, and report them. With homelab down, the same playbook names the scratch-volume fallback.
6. **Switch, on the go-ahead.** The how-to's step 8 has a `**Stop:**` line: the new version migrates the live database as it starts, and going back may then mean restoring the backup from step 3, losing what people save in the meantime. Ask the operator for the go-ahead for this step, quoting that line and the green result block, and wait for it. Then run `docs/how-to/run-project.md` (Recreate the container). Expect it healthy within two minutes. If it isn't, follow `docs/how-to/roll-back-upgrade.md`, whose start of the old version is a `**Stop:**` step too.
7. **Run the after-steps.**
   - The how-to's step 9, `docs/how-to/run-project.md` (Check the app), all four steps. The start-up line names the version from step 4 without its `v`, the commit from step 5, and the migrations the rehearsal applied. Check the app's step 4 logs in to production: ask the operator to do it, or list it as waiting.
   - Its step 10, when the maintenance webhook is on: the requests Zoho sent during the switch.
   - Its step 11, `docs/how-to/run-project.md` (Clean up old images) step 1 only. Keep `previous` until the new version has run well for a while.
   - The `TODO.md` notes from step 2. A finished item is deleted from `TODO.md` (`docs/directives/writing-docs.md`), on a branch.

Whether going back needs the backup is step 2 of If the new version started in `docs/how-to/roll-back-upgrade.md`: with the same MAJOR number, a switch to `previous` undoes the upgrade. With a higher one, it needs the backup only when a PR under "BREAKING CHANGES" in between says so.

Not established in bphs-connect: how an agent reaches the VPS (every command in the how-to runs in a shell there, in `/opt/bphs-connect`), whether an agent logs in to production, or a log of upgrades beyond `TODO.md` and the reply.

**Reply:** what ran, each step with its result; each `**Stop:**` step with the go-ahead it got; what is waiting, such as a step not run, a go-ahead not given, an operator check or a `TODO.md` item; and the rollback point: the release and commit from step 3, the `bphs-connect:previous` image, the backup's file name, and whether going back needs that backup.
