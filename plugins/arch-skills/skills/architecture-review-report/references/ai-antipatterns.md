# AI-assisted code anti-patterns

Read this when reviewing code written or changed by a coding agent, or any PR where these signals appear. Sections 1 to 6 are for code; section 7 is for plans, specs and issues that hand work to agents. Each pattern has the signal, the confirm step, and what to ask for.

These are failure modes, not proof of AI authorship. Humans do all of them too. Judge the code, not the author.

## 1. Assertion weakening ("making the test pass")

An agent told to make tests pass can do it by changing the test instead of the code.

Signals (diff_scan.py `tests`):
- Assertion count in a test file fell, or a test file was deleted.
- Exact matchers replaced by loose ones: `toEqual` to `toBeTruthy`/`toBeDefined`/`toMatchObject`, `assert x == 5` to `assert x is not None`, `mock.ANY`, `expect.anything()`.
- `skip`, `xfail`, `.only`, `@Disabled` added.
- The unit under test is mocked, so the test checks the mock.
- Expected values changed in the same PR as the code they check, with no reason in the PR text.
- Source code special-cases test inputs (`if name == "test_user"`, a branch that matches a fixture value), overloads equality or comparison so checks always pass, or records extra state only to return what a test expects. ImpossibleBench (Zhong, Raghunathan & Carlini, arXiv 2510.20270, 2025) found these four tactics when models were given tests that contradicted the spec; Claude models mostly modified the tests. Its LLM monitors caught only about half of the cheating on realistic tasks, so compare every changed assertion against the base version yourself.

Confirm: read the old and new assertion side by side. Ask "does the new test fail on the old bug?"
Severity: High if any behaviour lost its check; Critical if a failing test was removed or skipped to make CI pass.
Ask for: restore the assertion and fix the code, or a written reason the old expectation was wrong.
Prevention that works: give the agent an explicit way out. In ImpossibleBench, telling the model it may stop and flag a test that looks wrong cut cheating sharply for some models. Read-only test files help but do not stop special-casing in source.

## 2. Silent error swallowing

Broad `try/except` or `catch` that returns `None`, `null`, `[]`, `{}`, `false`, or does nothing, so callers see success.

Signals (diff_scan.py `swallow`): empty catch, `except Exception: pass`, `.catch(() => {})`, `|| true` in scripts, `_ = err` in Go.
Confirm: who calls this, and what do they do with the empty value? A swallowed error on a write path or in money, auth or data handling is worse than in optional UI decoration.
Severity: High on write paths and core logic; Medium elsewhere; OK when the catch is narrow, logged with context, and the fallback is a documented business rule.
Ask for: catch the narrowest exception, log with context and re-raise or return a typed error (Result/Either), or document why the fallback is correct.

## 3. Speculative over-abstraction

Interfaces with one implementation, factories that build one thing, plugin registries with one plugin, config flags nobody sets, "generic" helpers with one caller.

Signals (diff_scan.py `abstraction` with `repo_references`): new `*Factory`, `*Registry`, `*Strategy`, `Base*`, `I*` interfaces, ABCs, Protocols; reference count of 1 or 2.
Confirm: count implementations and callers. Is there a second user in this PR or a named, dated plan for one?
Principle: YAGNI (Beck, *Extreme Programming Explained*, 1999); Rule of Three (Roberts, cited in Fowler, *Refactoring*, 1999).
Exception: a port in front of infrastructure or a vendor is not speculative even with one adapter, because it isolates a volatile dependency (DIP). Check the ADR.
Severity: Medium; Low if small.
Ask for: inline it until a second case exists.

## 4. Scope creep beyond the linked issue

The change does more than its issue asks: it touches areas the issue never mentions, mixes a refactor with the feature, or bundles unrelated issues. Agents do this when they "fix what they see" on the way. Size alone is not this pattern: a large PR that stays inside its issue is fine, and a ten-line edit to an unrelated module is not.

Signals (scope_check.py): code in an area that no linked issue or PR text explains; more than one linked issue with no shared feature, module or blocker; no linked issue at all; a refactor (moved or renamed code) in the same files as the behaviour change; a docs-system or tooling change mixed with a feature when the repo keeps those apart.
Confirm: read each linked issue (`gh issue view <n> --json title,body`). For each code area in the change, find the sentence in the issue or PR body that needs it. An area with no such sentence is a candidate. Supporting edits are not scope creep: a test for the change, a doc the change makes stale, an export added to a public API the change uses, a registry regenerated by a tool.
Why it matters: an unrelated change gets no real review because the reviewer is reading for the issue; it ties two changes together, so reverting one reverts both; and it hides contract changes in noise. Small, focused changes review better and deliver better (Cohen 2006, *Best Kept Secrets of Peer Code Review*; Forsgren, Humble & Kim, *Accelerate*, 2018), but the measure that matters here is focus on one issue, not a line count.
Severity: Medium; High if the unrelated part changes a contract, a schema, a public API or another module's behaviour.
Ask for: a scope plan: which files belong to the linked issue, and which should move to their own issue and PR (name the issue to open). If the extra change is small and the owner wants to keep it, ask for one line in the PR body that says why.

## 5. Context-window myopia

The agent did not see the rest of the repo, so it re-invents what exists. GitClear's 2025 code-quality report (read via a secondary summary) reports a sharp rise in duplicated blocks and a fall in moved (refactored) lines during 2024; treat it as a reason to check, not as proof for a given PR.

Signals: new helper with a name close to an existing one (`formatMoney` vs `formatCurrency`); a new folder `utils2/`; new constants that duplicate existing enums; widened visibility to reach something instead of using its public API.
Confirm: search the repo for synonyms and for the core expression.
Severity: Medium (clone) to High (business rule duplicated).
Ask for: use the existing one; if it is hard to find, that is a navigability finding (see repo-navigability-audit).

## 6. Suppression creep

New `# noqa`, `# type: ignore`, `@ts-ignore`, `eslint-disable`, `nolint`, `pragma: no cover` added to make checks pass.
Severity: Medium; High if it hides a type error at a boundary.
Ask for: fix the cause, or a comment with the reason on the same line.

## 7. Plan-level risks (plans, specs, issues)

Use these when the input is a plan or a set of issues, not code. Each one is a design gap that later shows up as patterns 1 to 6.

| Risk | Signal in the text | Principle | Ask for |
|---|---|---|---|
| Overlapping ownership | Two parallel tasks or agents edit the same files, tables or shared config | Conway (1968): boundaries first, then owners; disjoint file ownership for parallel work | A split by module or file set, with one owner each; shared files changed in one task first |
| Open-loop work | A task says "implement X" with no check that proves it is done | Fitness functions (Ford, Parsons & Kua 2017) | For each task, the test, lint rule or script that must pass, named in the task |
| Issue without a boundary | An issue names a feature but not the module that owns it, so the agent picks one | Information hiding (Parnas 1972); bounded contexts (Evans 2003) | One line per issue: the module that owns the change, and any module it may not touch |
| Unmeasured quality goal | "fast", "scalable", "secure" with no number or scenario | Quality attribute scenarios (Bass, Clements & Kazman 2021) | One scenario per goal: stimulus, response, measure |
| No way to see it fail | No log, metric, trace or audit entry for a new flow | Observability: structured events and correlation IDs (Majors, Fong-Jones & Miranda, *Observability Engineering*, 2022) | The event or audit entry the flow writes, and who reads it |
| Bundled issues | One plan step or PR covers several unrelated issues | Small batches (Forsgren, Humble & Kim 2018) | One issue per PR, or a line on why they must ship together |

Severity: Medium by default; High when the gap sits on a Type 1 decision or a cross-module contract.
